# 6. Решения, риски и дорожная карта

## 6.1 Архитектурные решения (ADR)

| № | Решение | Обоснование | Альтернатива |
|---|---|---|---|
| ADR-1 | **JWT (HS256) + роли в claims** | Stateless-аутентификация подходит для SPA и мобильного клиента | Cookie-сессии |
| ADR-2 | **BCrypt** для паролей | Адаптивный алгоритм с солью | Argon2 — сильнее, но требует доп. зависимость |
| ADR-3 | **`userId` только из токена** | Исключает подмену идентификатора в запросе | — |
| ADR-4 | **Голоса — в таблице `Votes`** | Данные переживают перезапуск, работает несколько инстансов, есть история | Redis — избыточно для MVP |
| ADR-5 | **Статусная модель в домене** (`Approve/Reject` запрещены из финального статуса) | Правило BR-08 в одном месте, покрыто unit-тестами | Проверки в контроллерах |
| ADR-6 | **Заявка = заведение** (одна сущность, статус определяет видимость) | Простота MVP, нет дублирования данных | Отдельная таблица `Establishments` при росте функциональности |
| ADR-7 | **409 для конфликта состояния, 429 для лимитов** | Клиент различает причины отказа | Везде 400 |
| ADR-8 | **FluentValidation** | Декларативные правила валидации | DataAnnotations |
| ADR-9 | **Геокодинг через Nominatim с кэшем в БД** | Открытые данные без коммерческих сервисов (ТЗ 1, 5.3.2); кэш снижает нагрузку и даёт устойчивость к сбоям | Платные API (Google, Yandex) — противоречат ТЗ |
| ADR-10 | **Файлы на диске/томе, метаданные в БД** | Просто и достаточно для MVP; весь каталог входит в бэкап | S3-совместимое хранилище при росте |
| ADR-11 | **Отмена заявки = статус `Cancelled`, а не удаление** | Требование ТЗ: отменённые заявки остаются в суточном лимите | Физическое удаление (позволяет обойти лимит) |

## 6.2 Реестр рисков

| ID | Риск | Вероятн. | Влияние | Митигация |
|---|---|:---:|:---:|---|
| R-1 | Недостоверные заявки / спам | Выс. | Выс. | Обязательное подтверждение + модерация + лимит 4/сутки |
| R-2 | Накрутка голосов мультиаккаунтами | Сред. | Сред. | Верификация студенческого статуса (бэклог), лимит 15 дней |
| R-3 | Модераторы — узкое место | Сред. | Выс. | Метрика «заявки > 48 ч», уведомления модераторам |
| R-4 | Радиусный поиск считается в памяти приложения | Сред. | Сред. | PostGIS/`ST_DWithin` или bounding-box по индексу (NFR-07) |
| R-5 | Загруженные файлы могут содержать вредоносное содержимое | Сред. | Выс. | Проверка сигнатуры и размера; выдача с `nosniff`; перспектива — антивирусная проверка и внешнее хранилище (S3) |
| R-7 | Недоступность или лимиты внешнего геосервиса (Nominatim) | Сред. | Сред. | Серверный кэш ≥ 24 ч, отдача устаревшего кэша при сбое, ручной ввод; перспектива — собственный инстанс |
| R-6 | Устаревание скидок | Выс. | Сред. | Голосование; авто-пометка по `ValidityPeriod` |

## 6.3 Открытые вопросы

1. Порог «скидка неактуальна» (например, ≥ 5 голосов «нет» при перевесе): автоскрытие или флаг модератору?
2. Нужна ли верификация студенческого статуса на старте (почта вуза, ЕЛК)?
3. Допускается ли несколько скидок на одно заведение и как объединять дубликаты?
4. Срок хранения данных отклонённых заявок и вложений (152-ФЗ / GDPR)?

## 6.4 Дорожная карта

| Этап | Содержание |
|---|---|
| **MVP** | Auth + роли, каталог, заявки с файлами, автоподсказки и автообогащение, модерация, голосование, тесты, CI, Docker |
| **v1.1** | Жалоба на скидку; уведомления о статусе заявки; антивирус для вложений |
| **v1.2** | Гео-поиск в PostGIS; кэш каталога; rate limiting на уровне API |
| **v2.0** | Верификация студента; кабинет заведения; избранное; аналитика для заведений |
