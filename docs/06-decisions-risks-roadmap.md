# 6. Решения, риски и дорожная карта

## 6.1 Журнал архитектурных решений (ADR)

| № | Решение | Причина | Альтернатива |
|---|---|---|---|
| ADR-1 | **JWT (HS256) + роли в claims** вместо «dev-token-{id}» | Исходная заглушка позволяла представиться любым пользователем, зная его Guid | Cookie-сессии — не подходят для мобильного/SPA-клиента |
| ADR-2 | **BCrypt** для паролей | Пароли хранились в открытом виде; BCrypt — адаптивный, с солью | Argon2 — сильнее, но тянет доп. зависимость |
| ADR-3 | **`userId` только из токена** | Параметр запроса можно подменить (IDOR) | — |
| ADR-4 | **Голоса — в таблице `Votes`** | Раньше хранились в статическом словаре в памяти: терялись при перезапуске и не работали при >1 инстансе | Redis — избыточно для MVP |
| ADR-5 | **Статусная модель в домене** (`Approve/Reject` кидают исключение из финального статуса) | Правило BR-08 живёт в одном месте и покрыто unit-тестами | Проверки в контроллерах — дублирование |
| ADR-6 | **Заявка = заведение** (одна сущность, статус определяет видимость) | Простота MVP; нет дублирования данных | Отдельная таблица `Establishments` при росте функциональности (несколько скидок на заведение) |
| ADR-7 | **409 для конфликта состояния, 429 для лимитов** | Различимость для клиента; семантика HTTP | Везде 400 — теряется смысл |
| ADR-8 | **Единая валидация FluentValidation** | Декларативные правила вместо россыпи `if` | DataAnnotations |

## 6.2 Что исправлено относительно первой версии (аудит)

| # | Находка | Риск | Исправление |
|---|---|---|---|
| 1 | Пароль в открытом виде в БД | Критический | BCrypt (BR-10) |
| 2 | Токен `dev-token-{userId}`, нигде не проверяется | Критический | Подписанный JWT, `[Authorize]` |
| 3 | `/api/admin/*` без авторизации | Критический | `[Authorize(Roles = Moderator)]` |
| 4 | `userId` в query-параметре | Высокий (IDOR) | Идентификатор из claims |
| 5 | Голоса в статическом словаре | Высокий (потеря данных) | Таблица `Votes` + миграция |
| 6 | Повторное одобрение/отклонение заявки | Средний | Конечный автомат + 409 |
| 7 | Дублирование регистрации (`/auth` и `/users`) | Низкий | Единый `/api/auth/register` |
| 8 | CORS «любой origin» | Средний | Список origin из конфигурации |
| 9 | Пересчёт курса прибавлял максимум 1 | Низкий (баг) | Учёт всех пропущенных 1 октября |
| 10 | Нет тестов, CI, контейнеризации | — | xUnit (21 тест), GitHub Actions, Docker |

## 6.3 Реестр рисков

| ID | Риск | Вероятн. | Влияние | Митигация |
|---|---|:---:|:---:|---|
| R-1 | Недостоверные заявки / спам | Выс. | Выс. | Обязательное подтверждение + модерация + лимит 4/сутки |
| R-2 | Накрутка голосов мультиаккаунтами | Сред. | Сред. | Верификация студенческого статуса (бэклог), лимит 15 дней |
| R-3 | Узкое место — модераторы | Сред. | Выс. | Метрика «заявки > 48 ч», уведомления модераторам |
| R-4 | Радиусный поиск считается в памяти приложения | Сред. | Сред. | PostGIS/`ST_DWithin` или bounding-box по индексу (NFR-07) |
| R-5 | Файлы подтверждения не сохраняются | Выс. | Выс. | Хранилище (S3/диск) + антивирус, FR-09 |
| R-6 | Устаревание скидок | Выс. | Сред. | Голосование; авто-пометка по `ValidityPeriod` |

## 6.4 Открытые вопросы к владельцу продукта

1. Что считать порогом «скидка неактуальна» (например, ≥ 5 голосов «нет» при перевесе)? Автоскрытие или флаг модератору?
2. Нужна ли верификация студенческого статуса на старте (через email вуза `.edu`/ЕЛК)?
3. Допускается ли несколько скидок на одно заведение и как их объединять (дубликаты)?
4. Срок хранения данных отклонённых заявок и вложений (152-ФЗ / GDPR)?

## 6.5 Дорожная карта

| Этап | Содержание |
