# 1. Видение и границы проекта

## 1.1 Проблема

Студенческие скидки (кафе, книжные, кинотеатры, сервисы) существуют, но информация о них разрознена:
она лежит в соцсетях заведений, чатах университетов и на отдельных сайтах. Студент не знает,
**где** скидка действует, **на каких условиях** и **актуальна ли она сейчас**. Заведения, в свою очередь,
не имеют простого канала, чтобы донести предложение до студентов.

| Боль студента | Следствие |
|---|---|
| Скидки найти сложно, информация в разных местах | Студент не пользуется скидками, заведение теряет клиента |
| Условия неочевидны («по билету», «только будни») | Конфликты на кассе |
| Информация устаревает, проверить нечем | Падает доверие к любому источнику |

## 1.2 Цель продукта

Единый каталог **проверенных** студенческих скидок с картой/поиском и механизмом
**краудсорсинговой актуализации**: пользователи предлагают скидки, модераторы проверяют,
сообщество подтверждает актуальность.

### Метрики успеха (SMART-цели для MVP)

| Метрика | Целевое значение | Как измеряется |
|---|---|---|
| Доля заявок, обработанных модератором в течение 48 ч | ≥ 90 % | `ModeratedAt − CreatedAt` |
| Доля опубликованных заведений с ≥ 1 голосом за 30 дней | ≥ 40 % | таблица `Votes` |
| Доля отклонённых заявок с указанной причиной | 100 % | бизнес-правило BR-07 |
| Время ответа каталога (p95) | ≤ 500 мс | мониторинг API |

## 1.3 Стейкхолдеры и роли

| Роль | Интерес | Влияние |
|---|---|---|
| **Студент (User)** | Находить скидки, предлагать новые, подтверждать актуальность | Высокое — основной источник контента |
| **Модератор (Moderator)** | Поддерживать качество каталога, отсеивать недостоверное | Высокое — «ворота» публикации |
| **Заведение** (косвенно) | Привлечение студентов | Среднее — источник условий скидки |
| **Владелец продукта** | Рост базы, качество данных | Высокое |
| **Разработчик / DevOps** | Поддерживаемость, безопасность | Среднее |

## 1.4 Границы (Scope)

### В MVP (реализовано)

- Регистрация и вход, JWT-аутентификация, роли `User` / `Moderator`
- Каталог опубликованных скидок: поиск, фильтр по району, поиск по радиусу, сортировка, пагинация
- Подача заявки на скидку с фото-подтверждением, личный кабинет, отмена заявки
- Модерация: очередь, одобрение, отклонение с причиной, правка данных
- Голосование за актуальность скидки (да/нет) с ограничением частоты
- Контакты обратной связи

### Вне MVP (в бэклоге, см. [06](06-decisions-risks-roadmap.md))

- Хранение файлов-подтверждений (сейчас проверяется и принимается только факт загрузки)
- Верификация студенческого статуса через вуз
- Категории заведений, избранное, push-уведомления
- Личный кабинет заведения (self-service публикация)
- Геокодирование адреса (методы описаны в `openapi.yaml`, реализация — в бэклоге)

## 1.5 Допущения и ограничения

- **A-1.** Студент подтверждает право на скидку на кассе; сервис не выдаёт промокоды.
- **A-2.** Достоверность проверяет модератор вручную по фото/ссылке на источник.
- **A-3.** Фронтенд (SPA / мобильное приложение) — отдельный клиент; этот репозиторий — бэкенд и контракт API.
- **C-1.** Стек: .NET 9, PostgreSQL, EF Core.
- **C-2.** Персональные данные пользователя — минимальные (email, имя, вуз, курс, Telegram по желанию).

## 1.6 Глоссарий

| Термин | Определение |
|---|---|
| Заявка (Application) | Предложение добавить скидку; проходит модерацию |
| Заведение (Establishment/Place) | Заявка в статусе `Published`, видимая в каталоге |
| Модерация | Проверка заявки модератором: одобрить / отклонить |
| Голос | Отметка «скидка актуальна / неактуальна» от пользователя |
